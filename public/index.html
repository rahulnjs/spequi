    A few things
    worth knowing.

    How does Spequi work with my coding agent?

    The Spequi skill runs inside your existing coding session. It starts the local server, listens for requests, and uses your installed OpenSpec workflows. Keep that session running while you work. Spequi does not launch a second coding agent.

    Do I need OpenSpec already installed?

    Yes. Install the OpenSpec CLI and its workflow skills separately. Spequi initialization registers the UI skill and project launchers. The setup guide explains the prerequisites.

    When does it change files in my project?

    Planning requests create or revise specification files in your project. Implementation previews run in an isolated copy. Applying a reviewed implementation is a separate action with explicit confirmation, conflict checks, and recoverable backups. The copy is not an OS security sandbox.

    Does every code change have a linked requirement?

    Link coverage depends on the preview and the metadata recorded by your agent. Spequi distinguishes recorded links, suggested file-level context, and files without supported links. A link helps you review intent; it does not prove correctness.

    What data leaves my machine?

    Spequi sends usage and failure metadata, including a persistent identifier, project folder name, and Git user name when configured. Source files, prompts, and review comments are excluded. Set SPEQUI_ANALYTICS_DISABLED=1 to opt out before initialization and startup. Your coding agent retains its own provider settings. See analytics and privacy.

    Getting started

    Requirements

    • Node.js 20+ and npm
    • A target project containing OpenSpec files

    For agent-driven planning and implementation you also need:

    • The OpenSpec CLI and its workflow skills, available to your coding agent
    • A skill-capable coding agent, attached with the spequi skill

    The current OpenSpec CLI requires Node.js 22.12+, independently of Spequi's Node.js 20 minimum. Use Node.js 22.12+ for the complete setup.

    Browsing, review, offline affected-file analysis and patch import work without an attached agent. Initializing this package installs the UI skill and command wrappers; OpenSpec setup and its workflow skills are separate.

    Initialize with npx

    cd /path/to/your-project
npx spequi@latest init

    Start with your agent

    Open the same project in your existing coding agent and invoke the Spequi skill in the agent's input, using its command below. These are agent commands, not terminal commands. Spequi does not launch a model or need a separate provider API key.

    Agent Invoke after initialization
    Claude Code /spequi (use /spequi init for setup)
    Codex $spequi, or select the viewer skill
    Sber/GitVerse GigaCode CLI /skills spequi or /spequi
    Other skill-capable agents Load .agents/skills/spequi/SKILL.md using the tool's own convention

    Reload your agent if newly generated commands or skills do not appear.

    The skill starts the local server, shares its URL, and consumes queued requests. Open the URL it provides, normally http://127.0.0.1:4310, or use your agent's browser tools. Browser opening is not automatic. Keep the agent session running while using the workspace.

    Without an attached agent, planning and implementation requests wait in the queue and everything else keeps working. Closing the agent pauses consumption and leaves requests saved.

    Each job runs the matching installed OpenSpec workflow in the same agent session:

    Job Workflow skill
    Preview implementation openspec-apply-change
    Proposals openspec-propose
    Feedback updates openspec-update-change
    Archive openspec-archive-change

    Exploration and verification use their corresponding workflows when available, with read-only fallbacks. Impact reports run directly. Missing required workflows fail the job with an explanation; they are never installed automatically.

    To upgrade an initialized project, refresh its managed launchers and skill, then invoke the skill again:

    npx spequi@latest init

    GigaCode notes

    GigaCode uses monitored Shell calls with is_background: true for the server and five-minute agent wait calls. Background completion must resume the host session for unattended idle attachment to work. The skill includes a check and a foreground fallback. Registration is tested; continuous polling in a real GigaCode session is not yet verified.

    Planning workflow

    Start a spec from an idea

    Choose New spec in the left panel. Describe the idea and give it an unused lowercase change name, then pick:

    • Start with the next artifact (default), or
    • Generate the full plan to request all required planning artifacts.

    Continue queues one planning request for the attached agent. Its questions stay in the app, replies survive reloads, and the generated change opens in its draft workspace when the request completes. Partial plans offer the next schema-ready artifact. Planning never starts implementation automatically.

    Ideas save under Drafts in the left panel. Return there to resume or delete a draft. Deleting a draft can also remove its generated planning files, after confirmation.

    Planning stages

    New specs and unfinished drafts show three stages in the header: Shape spec, Implement, Validate & archive. Existing changes open in document review from the left panel. Continue a draft or open a planning request from Requests to return to its planning workspace.

    Shape spec

    • Select a planning artifact tab and use Revise spec to request an update, or Ask a question for a read-only exploration.
    • Changes appear as highlighted sections with a document summary. Highlights begin with revisions to existing text.
    • Artifacts with several documents use a dropdown showing each file's relative path and a description from its content.
    • Planning actions offers the next artifact or the full plan.
    • Documents are read-only in the viewer.

    Implement

    • Generate an isolated preview and choose its version.
    • Browse changed files beneath the selected change in the left panel. The Files button brings the list into view.
    • Previous/next controls, the selected file and diff tools stay above the independently scrolling code.
    • Inspect the actual diff, then confirm Apply reviewed preview. A changed spec or a source conflict prevents applying.
    • A preview becomes stale when its planning documents change. Generate a fresh one before applying.

    Offline analysis, optional model proposals and patch import also live here. See Offline tools.

    Validate & archive

    Distinguishes local spec validation from agent implementation verification, and exposes sync and archive with their normal prerequisites. Archive confirmations appear in the conversation.

    Status, task readiness and strict validation use the installed openspec CLI locally, with no agent required. Missing or incompatible CLI capabilities disable those actions with an explanation. Checked task boxes alone do not prove the implementation is correct.

    Commands

    The Commands picker shows the next executable command and previously completed commands. While a request is pending, it shows the request status and a link to the conversation. Dropdowns close when clicking outside or pressing Escape.

    The picker and typed slash commands use the same guarded operations. Supported commands are:

    Command Purpose
    /new Start a new spec
    /explore <question> Read-only exploration
    /continue Create the next planning artifact
    /propose Generate the full plan
    /update <revision> Request a planning revision
    /apply Generate an isolated implementation preview (writing files still needs the separate Apply confirmation)
    /status Show change status
    /validate Run strict spec validation
    /verify Verify implementation with the agent
    /sync Sync specs
    /archive Archive the change

    /opsx:<name> and /opsx-<name> aliases also work. These are app commands, independent of the host agent's slash-command installation.

    Questions and agent handoff

    Reasoning and writing requests use the current session running the viewer skill. The agent asks questions with agent ask and waits for the app's reply with agent input --wait 300. The job resumes with the same ownership token.

    • Queued and awaiting-input requests can be cancelled.
    • A running request can be ended only after its owning session's heartbeat expires. Stop the old agent in your coding tool first; ending a request does not terminate its process or undo its edits.
    • Keep the agent session attached to continue waiting work.

    Planning history

    Planning versions are kept under .spequi/studio/. A revision stores the exact Markdown before a request and after it completes. The most recent 40 versions are retained, with at most 8 MiB of planning documents per version. This is local review evidence; the files under openspec/ remain the source of truth.

    Review workflow

    Choose Review - Inspect & comment to examine a change through Proposal, Design, Tasks and Files.

    Documents

    Proposal, Design and Tasks support rendered Markdown and a source view.

    Files and diffs

    Files compares the current project with the proposed implementation:

    • Unified or Split diffs
    • Syntax highlighting and changed-word emphasis
    • Context folding and line wrapping
    • An inspector that follows the selected file with dependency impact and saved comments

    Spec context in diffs

    In both diff modes, linked change blocks show the requirement, scenario or planning decision behind the edit. Each quote includes its source path and line range from the preview's retained baseline. Collapse a quote to focus on code; repeated links point back to the first quote.

    The attached agent records code-to-spec locations while implementing. Older previews and imported patches can show Suggested - file-level context when the saved plan mentions the file or a changed symbol. Suggestions need reviewer confirmation, and files without a supported match say so explicitly.

    To enable recorded links for new previews, refresh the skill: node .spequi/cli.mjs skill install. Format details: agent metadata format.

    Impact analysis

    The inspector lists direct and downstream dependencies, related tests and export changes, with explicit static-analysis limitations. See Security and limits.

    Comments and feedback

    Comment on a whole file, a code range, or a passage in Proposal or Design. Notes retain the exact reviewed version.

    • Export MD downloads an immutable Markdown review brief.
    • Update spec queues a planning revision for the attached agent from that exact snapshot.

    Exporting feedback does not edit a specification or apply code. Spec revisions and implementation previews are separate actions. Generate a fresh preview when the plan changes.

    Requests inbox

    Open Requests in the header for an inbox grouped by spec.

    • Questions, failures and stalled work appear first, then running and queued work.
    • The badge counts specs needing attention.
    • A collapsed Recent section holds the latest five completed specs. Cancelled and older work stays in All history, with status filters and pagination.
    • Dismiss clears settled items from the inbox while preserving requests, previews and comments.
    • Cancel and supported retry actions stay available. Destructive deletion is confined to history.
    • Active work stays visible while you browse another spec. Partially edited planning work must be reviewed before continuing.

    How Spequi attaches an agent and runs skills

    This document describes the current implementation: how the app hands work to an existing coding agent, how that agent follows another skill, how questions wait for an answer in the UI, and how results return to the app.

    The app does not call a model or start a coding agent. You invoke the spequi skill in an existing agent session. That agent runs local CLI commands, reads workflow instructions, performs the work through its tools, and reports completion.

    There is no await invokeSkill() implementation. A skill is an instruction document that the current agent reads and follows. Completion is an explicit job update, not a return value from another skill process.

    1. The components

    Component Responsibility Implementation
    Browser UI Submit actions, display progress, collect answers public/workflow.js, src/studio-view.mjs
    Local server Protect browser mutations, route actions and replies, notify the UI src/server.mjs
    Lifecycle layer Check readiness and enqueue the requested action src/lifecycle.mjs
    Job queue Persist requests, claim ownership, choose workflows, store results src/jobs.mjs
    Agent CLI Report a session, poll, ask, wait, log, finish or fail bin/spequi.mjs
    Session evidence Store credential-free agent/MCP reports and evaluate freshness src/agent-session.mjs
    Question storage Retain questions and answers on the same owned job src/job-dialogue.mjs
    Agent skill Instruct the current agent to coordinate the loop spequi SKILL.md

    The browser talks to the server over local HTTP and receives WebSocket notifications. The agent’s CLI commands use the project server’s authenticated loopback protocol when it is running. .spequi/server.json binds that connection to the project root; an unavailable saved connection is an explicit restart error. Headless commands without a server retain the file protocol. They do not send prompts over the browser's WebSocket connection.

    Typical retained state looks like:

    .spequi/
  cli.mjs                 Project launcher for the initialized package
  server.mjs              Project server launcher
  server.json             Private root-bound agent protocol connection
  drafts/                 Autosaved ideas and unfinished planning references
  agent.json              Latest agent heartbeat
  agent-session.json      Session ID and reported MCP metadata
  jobs/
    <job-id>.json          Action, ownership, status, questions, logs and result
  previews/
    <job-id>/
      baseline/           Files captured before implementation
      work/               Isolated project copy assigned to the agent
      proposed/           Frozen changed files after completion
      manifest.json       Baseline fingerprints
      result.json         Diff metadata and application state

    2. Attachment starts in the coding agent

    The user invokes the installed skill using the host's convention, such as $spequi in Codex, /skills spequi in Sber/GitVerse GigaCode CLI, or /spequi in a CLI with that wrapper. The host makes the skill instructions available to the existing agent session.

    The skill tells the agent to reuse the project's initialized launcher and existing server. This avoids requiring a global installation or starting a second agent.

    GigaCode registration

    The installer registers GigaCode alongside the existing agents. Project initialization and skill install create:

    .gigacode/
  skills/spequi/SKILL.md
  commands/spequi.md

    skill install --global creates the same paths under the user's home directory. The command wrappers reference the skill in the matching scope and use GigaCode's {{args}} parameter syntax. After discovery, invoke /skills spequi or /spequi. These paths and formats follow GigaCode's skills and commands documentation.

    The installer registers the viewer skill; it does not install other OpenSpec workflows. Those must be discoverable separately. Registration and refresh behavior are tested locally; indefinite polling in a real GigaCode session still requires an integration test.

    Register a session

    The agent creates a small report under .spequi. This is an illustrative report, not a real attachment identifier:

    {
  "sessionId": "example-attachment",
  "mcps": {
    "supported": false,
    "connections": []
  }
}

    Then it runs this command from the project root:

    node .spequi/cli.mjs agent report \
  --file .spequi/session-report.json \
  --name Codex

    reportSession() validates the report and stores the attachment evidence. The essential writes are:

    const report = {
  agent,
  sessionId: id,
  reportedAt: Date.now(),
  mcps: { supported: mcps.supported, connections },
};

await writeJSON(runtime(root, "agent-session.json"), report);
await writeJSON(runtime(root, "agent.json"), {
  agent,
  sessionId: id,
  at: Date.now(),
});

    Source: reportSession().

    This session ID belongs to the viewer attachment. It is not a provider API credential or an integration with the coding tool's internal conversation ID. The agent retains it and uses it on subsequent polls.

    Wait, then claim

    node .spequi/cli.mjs agent wait --wait 300 \
  --name Codex --session-id example-attachment

    In GigaCode, launch this bounded wait and the retained server using the host Shell tool’s is_background: true argument. Keep the task ID and monitor the completion result. The wait refreshes consumer liveness and returns available: true when work is available, without claiming it. Once this session receives the output, claim in the foreground:

    node .spequi/cli.mjs agent next --wait 0 \
  --name Codex --session-id example-attachment

    A first-attachment agent wait --wait 1 checks host completion delivery. If GigaCode does not resume the session automatically, use its task monitor or retained foreground polling; a background process alone cannot wake the model. Attachment lasts while the coding session remains open, including idle periods supported by that notification mechanism.

    Waits are bounded at five minutes and check for work every 250 ms. An empty result includes queue state. Contention and blocked locks are errors, never an empty queue. An owned active request blocks additional claims. Finish or answer it before claiming another; review partial planning work before any retry.

    Source: agent CLI, root-bound client, and agent protocol routes.

    3. A UI action becomes a durable job

    For example, a user requests an implementation preview. The browser submits the selected change to the lifecycle route:

    // Simplified browser request. The selected change must already be ready.
await fetch("/api/lifecycle/actions", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Accept: "application/json",
    "X-CSRF-Token": document.querySelector("meta[name=csrf-token]").content,
  },
  body: JSON.stringify({
    action: "preview",
    change: "example-change",
  }),
});

    The server checks the local request boundary. The lifecycle layer checks whether the selected action is permitted, then creates a queued job. A simplified shape is:

    {
  "id": "example-job-id",
  "action": "preview",
  "change": "example-change",
  "status": "queued",
  "message": ""
}

    The job is written under .spequi/jobs/. It remains available if the browser reloads or no agent is currently polling.

    Source: requestLifecycle() and createJob() / enqueue().

    4. Claiming establishes ownership and selects the skill

    claimNext() updates the heartbeat, acquires the queue lock and selects the oldest queued request. It changes the job to running, assigns a random claim token and records the agent attachment identity. Only one workflow runs per project. The short claim releases the queue lock before snapshot copying or plan capture; preparation failures are retained as failed requests. Locks record their process owner and recover abandoned dead-owner or aged legacy empty files. Live lock contention remains explicit.

    The claim token is required for the agent's subsequent log, question, input and completion commands. A second agent cannot complete the same job just by knowing its ID.

    The action-to-skill mapping currently includes:

    const skillRoutes = {
  explore: { skill: "openspec-explore", required: false },
  propose: { skill: "openspec-propose", required: true },
  preview: { skill: "openspec-apply-change", required: true },
  verify: { skill: "openspec-verify-change", required: false },
  archive: { skill: "openspec-archive-change", required: true },
  impact: { skill: null, required: false },
  "update-specs": { skill: "openspec-update-change", required: true },
  "create-change": { skill: null, required: false },
  "start-plan": { skill: null, required: false },
  "plan-next": { skill: null, required: false },
  "revise-plan": { skill: "openspec-update-change", required: true },
  "sync-specs": { skill: "openspec-sync-specs", required: true },
};

    Full-plan start-plan requests use the proposal route. Next-artifact requests use the bounded CLI workflow directly; they do not require another skill.

    After selecting the route, claimNext() constructs the workflow:

    job.workingDirectory =
  job.action === "preview" ? await createPreview(root, job.id) : root;

job.workflow = {
  mode: "same-session",
  ...(job.action === "start-plan" && job.planMode === "full"
    ? skillRoutes.propose
    : skillRoutes[job.action]),
  directory: job.workingDirectory,
  protocolDirectory: root,
  change: job.change,
};

job.instructions = instructions(job);

    Source: skillRoutes, instructions() and claimNext().

    5. What “invoke another skill” actually means

    The CLI returns a job containing a workflow such as this abbreviated example:

    {
  "action": "preview",
  "workflow": {
    "mode": "same-session",
    "skill": "openspec-apply-change",
    "required": true,
    "directory": "/project/.spequi/previews/example-job-id/work",
    "protocolDirectory": "/project",
    "change": "example-change"
  }
}

    The returned instructions explicitly tell the agent to load and follow that installed skill in the current session. They also prohibit starting another coding-agent process, subagent or model endpoint for the handoff.

    The agent locates the skill through its host's skill discovery. In this repository, reading the apply skill can look like:

    cat .agents/skills/openspec-apply-change/SKILL.md

    Reading that file does not execute a skill. It gives the agent instructions. The agent then carries out those instructions through its normal tools: resolving OpenSpec status, reading artifacts, editing the assigned files and running checks.

    For example, the apply workflow includes commands such as:

    # Run from the job's workflow.directory, which is the isolated copy for previews.
openspec context --json
openspec status --change example-change --json
openspec instructions apply --change example-change --json

    The same agent continues the task after reading the skill. There is no separate skill process to await, no injected slash command, and no new model session whose response must be collected.

    If a required skill is missing, the agent must report failure instead of claiming the workflow ran. Optional read-only workflows have their documented direct-execution fallback.

    The behavior contract lives in the same-session routing section of the skill. It is an agent instruction contract, not a JavaScript skill execution engine.

    6. Preview work uses two different directories

    For an implementation preview:

    Directory What happens there
    workflow.directory Read the copied planning context, implement, install needed dependencies and run checks inside the isolated copy
    workflow.protocolDirectory Run agent log, ask, input, finish and fail against the original project's queue

    All implementation edits, including task checkboxes, stay inside the preview copy. The agent must re-resolve OpenSpec roots there and refuse paths that escape it. The snapshot is not an OS sandbox; the agent must honor that boundary.

    When the agent finishes, the application freezes the resulting changed files. It does not copy them into the original project automatically. The user reviews the diff and explicitly uses Apply reviewed preview, which checks for baseline conflicts.

    Source: createPreview(), freezePreview() and applyPreview().

    Spec links in implementation previews

    Before finishing, the agent writes .spequi/spec-links.json inside workingDirectory. The job instructions and installed spequi skill include this format:

    {
  "version": 1,
  "links": [
    {
      "file": "src/preferences.js",
      "side": "proposed",
      "start": 12,
      "end": 18,
      "spec": "openspec/changes/email-preferences/specs/email-preferences/spec.md",
      "specStart": 3,
      "specEnd": 9
    }
  ]
}

    Code and spec ranges are one-based and inclusive. Use final proposed line numbers for additions or modifications, or "side": "current" and baseline line numbers for deletions. Cite the original copied plan, with a range that explains the changed code. Supported sources are Markdown artifacts in the selected change and main specs under openspec/specs/**/spec.md. Do not invent links for unexplained edits.

    On completion, the viewer validates that code ranges overlap actual changes, retains at most eight links per changed file, and verifies up to 80 spec lines per quote against the baseline manifest. It stores locations and fingerprints in result.json; quoted text is always read from the retained baseline. Invalid links are omitted with a notice. The report is optional, limited to 64 KiB and 100 links, and excluded from proposed source and application.

    Both Unified and Split diffs show Agent linked quotes beside the corresponding change blocks. Repeated references link to the first quote. Old previews and imported patches without recorded links can receive Suggested · file-level quotes based on explicit file paths, unique filenames, or backticked changed identifiers in the saved change artifacts. These are candidate context, not evidence of why a specific block changed. No match or unavailable snapshot remains explicit; the viewer does not substitute the current working plan.

    Source: spec-context.mjs, spec-context-view.mjs.

    7. Questions wait for an answer through the same job

    If the selected workflow needs clarification or confirmation, the agent runs the following from workflow.protocolDirectory. JOB_ID and CLAIM_TOKEN stand for values returned by the claim; they are not literal identifiers to reuse.

    node .spequi/cli.mjs agent ask JOB_ID \
  --token CLAIM_TOKEN \
  --message "Which authentication method should this change support?" \
  --options '["OAuth","Environment variable"]'

    askJob() verifies ownership, saves the question and transitions the job:

    const question = {
  id: randomUUID(),
  message: message.trim(),
  options,
  askedAt: new Date().toISOString(),
};

(job.questions ||= []).push(question);
job.status = "awaiting-input";

    The agent then waits with:

    node .spequi/cli.mjs agent input JOB_ID \
  --token CLAIM_TOKEN --wait 300

    The CLI checks the owned job every 250 ms until the status changes or the bounded wait expires. If it is still awaiting-input, the agent repeats the bounded wait. It does not release the job or make a second claim.

    The user answers through this protected browser route:

    POST /api/lifecycle/jobs/<job-id>/reply

    answerJob() checks that the submitted question is still current and unanswered, then stores the answer:

    question.answer = answer.trim();
question.answeredAt = new Date().toISOString();
job.status = "running";

    The next agent input result contains that retained answer. The current agent reads it and resumes the same workflow. If the request is cancelled instead, the agent stops that work rather than continuing or waiting indefinitely. Browser reloads do not discard the question or answer because both are stored on the job.

    Source: askJob(), answerJob() and jobInput(), plus the reply route in src/server.mjs.

    8. Progress and completion are explicit

    While working, the agent reports meaningful progress:

    node .spequi/cli.mjs agent log JOB_ID \
  --token CLAIM_TOKEN \
  --message "Implemented the form; checking validation and keyboard behavior."

    On success:

    node .spequi/cli.mjs agent finish JOB_ID \
  --token CLAIM_TOKEN \
  --message "Implemented the requested scope; checks passed."

    On failure:

    node .spequi/cli.mjs agent fail JOB_ID \
  --token CLAIM_TOKEN \
  --message "The required workflow is unavailable; implementation did not run."

    updateJob() checks the token and current state. It performs action-specific completion checks, such as requiring actual new planning artifacts, checking full-plan readiness, validating an impact report or freezing an implementation preview. It then persists the result:

    job.status = "completed";
job.result = message || "Completed";

    The app waits for this explicit completion. It does not infer completion because the agent read a skill, produced a chat response, checked some task boxes, or stopped polling. The checks also do not prove every instruction was followed or every behavior is correct; verification and code review still matter.

    After finishing or failing, the agent returns to agent wait, then claims in the foreground while attached.

    Source: updateJob().

    9. Liveness, MCP evidence and recovery

    The current heartbeat check is:

    const connected = Boolean(state && Date.now() - state.at < 45000);

    A recent heartbeat means the attachment has recently communicated. It does not prove a particular model request is progressing. Likewise, a missing heartbeat does not prove the coding process crashed: a long tool call or an agent that stopped running the loop can also make the attachment appear unresponsive.

    Polling and owned log/input/question calls refresh the heartbeat. A session report alone means connected, not ready. Ready additionally requires a current consumer wait lease; finishing or disconnecting that wait clears readiness. Working and awaiting-input states follow the owned request. The header exposes queued counts, last heartbeat and blocked/stalled ownership separately. The agent must keep communicating during work; the implementation does not start an independent background heartbeat daemon.

    MCP status is a separate report. The host must supply authoritative connection evidence; a configured server or a tool catalog alone is insufficient. Reports contain display names and allowed connection states, not credentials or transport configuration. MCP evidence also expires after five minutes and must match the current attachment.

    The header displays MCPs when current connection evidence is unavailable. 0 MCPs requires a fresh supported report confirming zero connected servers.

    If the agent becomes unresponsive:

    1. Resume the spequi skill in the existing coding session.
    2. Check the agent indicator's recovery details and last heartbeat.
    3. If an old running request is stuck, stop its agent in the coding tool first. The app permits ending that request after its owner's heartbeat expires, then a new request can be submitted.

    Ending a request changes queue state; it does not terminate an agent process or undo edits. Reattaching does not automatically reclaim or restart an old running job. The app cannot wake a stopped agent session by itself.

    Source: heartbeat() and agentStatus(), session freshness, and the header/recovery UI.

    10. The complete sequence

    sequenceDiagram
    actor User
    participant UI as Browser UI
    participant App as Local server and job files
    participant Agent as Existing coding-agent session
    participant Skill as Installed SKILL.md

    User->>Agent: Invoke spequi
    Agent->>App: agent report and monitored agent wait
    User->>UI: Request a workflow
    UI->>App: POST lifecycle action
    App->>App: Persist queued job
    Agent->>App: agent next
    App-->>Agent: Owned job, skill name, directories, instructions
    Agent->>Skill: Read the selected skill
    Skill-->>Agent: Workflow instructions
    Note over Agent: The same agent executes the workflow through its tools
    opt Clarification needed
        Agent->>App: agent ask
        App-->>UI: Question available
        par Agent waits
            loop While awaiting-input
                Agent->>App: agent input --wait 300
                App-->>Agent: Current question and status
            end
        and User answers
            User->>UI: Submit answer
            UI->>App: POST job reply
        end
        Note over Agent,App: The input result contains the retained answer and running status
    end
    Agent->>App: agent log
    Agent->>App: agent finish or agent fail
    App->>App: Validate completion and persist result
    App-->>UI: Updated status and result
    Agent->>App: Return to monitored agent wait

    The queue, ownership, persistence, questions and status checks are application code. Carrying out a selected skill is the cooperating agent's work in its existing session. Keeping those responsibilities explicit explains both why the flow works across skill-capable coding tools and why it pauses when the agent stops serving the queue.

    Agent liveness and MCP reports

    Merge this section into your existing docs/agent-workflow.md (it already covers queue, skill routing and spec links).

    The header's agent indicator reflects a recent agent heartbeat, independent of the browser's connection to the local server. It distinguishes: live, working, awaiting an answer, not responding, and unattached. Connection details show the last heartbeat and MCP metadata reported by the current session.

    Reconnect agent opens instructions to resume the spequi skill in the same coding session, with a Check connection action. Requests and answers stay saved. Spequi never restarts an agent automatically.

    Reporting MCP status

    The agent can write a credential-free report under .spequi, then run:

    node .spequi/cli.mjs agent report --file .spequi/session-report.json --name "Spequi Agent"

    {
  "sessionId": "a-stable-random-id-for-this-attachment",
  "mcps": {
    "supported": true,
    "connections": [{ "name": "Filesystem", "status": "connected" }]
  }
}
    • Allowed statuses: connected, disconnected, unavailable, unknown.
    • Only display names and statuses are accepted. Omit credentials, server URLs, environment variables and transport configuration.
    • If the host cannot enumerate connection status, report {"mcps":{"supported":false,"connections":[]}}.
    • A tool catalog or a configured server alone is not evidence of a healthy connection.
    • Keep the returned session ID for refreshes, pass it as agent next --session-id <id>, and use the same agent name when polling.
    • Refresh at least every five minutes or whenever connections change.
    • Missing, expired or disconnected-session reports show as unknown, never as a fabricated count.
    • The header shows MCPs when the session has not supplied evidence, and 0 MCPs only when a fresh supported report confirms zero.
    • Reporting does not replace serving the agent queue.

    Offline tools and model preview

    These tools live under Build > Implement > Offline analysis and preview tools and need no attached agent.

    Analyze affected files

    Matches the selected change's planning documents to current source, with no agent and no network. It explains explicit paths, named symbols, related text and local dependencies separately from actual changed files.

    Limits:

    • At most 1,000 text files, 512 KB per file, and 8 MiB of source
    • Planning documents limited to 2 MiB total
    • Exclusions, skipped files, unresolved references and stale inputs are disclosed
    • Dynamic references, aliases, external packages, and dependencies outside supported JS/TS, CSS and HTML forms can be missed

    Import patch

    Stages a unified patch in a separate project copy.

    • Add, modify or delete up to 30 eligible UTF-8 files
    • 1 MiB limit for the patch and proposed content
    • Renames are represented as a deletion plus an addition
    • Review the saved diff, export it, comment on it, or apply it through the normal baseline conflict checks
    • A failed import never publishes a partially completed preview

    Optional model generation

    For generation without an agent session, add previewModel to .spequi/config.json, keeping the other settings:

    {
  "version": 1,
  "port": 4310,
  "previewModel": {
    "endpoint": "http://127.0.0.1:11434/v1/chat/completions",
    "model": "your-installed-model",
    "timeoutMs": 120000
  }
}
    • The endpoint must accept Chat Completions-compatible JSON and return text at choices[0].message.content. A local runtime keeps generation offline.
    • Hosted endpoints require HTTPS. Plain HTTP is accepted only for loopback hosts.
    • If authentication is needed, set "apiKeyEnv": "SPEQUI_PREVIEW_API_KEY" and provide that environment variable to the viewer process. Never put a key in the endpoint URL.
    • No model is installed or downloaded by Spequi.

    Workflow: Analyze first, select 1 to 12 candidate files, then choose Generate with model.

    Privacy: this action sends the change's planning documents and the selected files to the displayed destination, and nothing else.

    Limits and guardrails:

    • Combined input is limited to 256 KB; output to 30 edits and 1 MiB of proposed source
    • Stale analyses require a new scan
    • Existing files outside the selected context, secrets, planning artifacts, agent configuration and escaping paths cannot be edited
    • Eligible new source files can be added
    • The model returns file contents only. Spequi runs no tools, shell commands, installations or tests

    Generated and imported previews show their origin and unrun-check status. Review and test before applying.

    Security and limits

    Local data and boundaries

    • The server binds to 127.0.0.1. Mutations require local Host/Origin checks and a session token.
    • .spequi/ holds local configuration, requests, previews, feedback and backups. Keep it out of Git.
    • Browsing and offline analysis do not upload project source.
    • Explicit model generation sends the planning documents and selected source to the configured endpoint.
    • Your attached agent keeps its own provider and permission settings.
    • All styles, scripts (including HTMX) and fonts are served locally. DM Sans and IBM Plex Mono are bundled with their licenses, so the UI needs no CDN or internet. Installing and recovering packages through npm still needs registry access unless packages are already available locally.

    Analytics

    Spequi sends usage and failure events to https://data.rahulnjs.com/api/spequi/sub/events (app_name: spequi, subject: events). Payloads include a persistent identifier shared across projects on the same machine account, the project folder name, Git user.name when configured, UTC timestamps, and event-specific identifiers, counts, and failure categories. Source files, prompts, review comments, and raw error messages are excluded.

    Events cover daily project activity, new spec creation, viewed file diffs, failed requests, and unavailable or failed diffs. Delivery is best effort, with one attempt and no retries. Analytics failures do not block the workspace. Set SPEQUI_ANALYTICS_DISABLED=1 before initialization and startup to disable analytics. CI sets this automatically.

    The attached agent may send project context to its own provider. Optional model generation sends planning documents and selected source to the configured endpoint.

    Applying changes

    • Previews are isolated copies of the project.
    • Planning requests create or revise specification files in the original project; implementation previews use the isolated copy.
    • Applying is always an explicit confirmation.
    • The apply API checks retained hashes and baseline conflicts before writing, and keeps recoverable backups.
    • LF and CRLF comparisons use normalized display lines; hashes, patches and application preserve the exact reviewed bytes.

    Known limitations

    • A preview copy is not an OS security sandbox. The agent must honor its assigned working directory.
    • Static impact evidence does not establish complete runtime behavior, dynamic references, aliases or external-package effects. Scan limitations stay visible in the UI.
    • Native Windows execution is a release verification item.
    • Continuous polling in a real GigaCode session has not been verified.
    • Agent attachment depends on the host agent resuming its session when background work completes.

    Architecture and development

    Stack

    Node.js ES modules, server-rendered HTML, HTMX, WebSockets, plain CSS and JavaScript. No frontend compilation and no hosted backend. Runtime dependencies handle file watching, Markdown sanitization, syntax highlighting, diffs and WebSocket transport.

    Layout

    bin/          Executable CLI
src/          Server, project reader, previews, impact and review implementation
public/       Runtime styles and browser JavaScript
skills/       Maintained portable agent skill
templates/    Self-contained project launcher template
scripts/      Maintenance scripts
test/         Tests
docs/         Documentation and README screenshots (excluded from the npm package)

    Development

    npm ci
npm run check
npm pack --dry-run
npm publish --dry-run

    There is no build step. package.json files limits the npm archive to runtime code and assets, the portable skill, the launcher template, package metadata, README and license. Publication runs syntax checks first.

    Naming

    The app is Spequi. The npm package, shell command and agent skill are all spequi: $spequi in Codex, /spequi in tools that support command wrappers. Initialization creates .spequi/ for local configuration, queued jobs, previews, comments and backups.
